# Conflux 产品化设计规格

**日期：** 2026-08-30
**状态：** 草案，等待规格审阅
**目标版本：** 0.2.0 产品化基础版本

## 1. 背景与目标

Conflux 当前已经具备会话图谱、共享上下文、异步消息、运行时智能体、MCP、HTTP API 和 Electron 开发壳。下一阶段不再把 Electron、Codex 支持和 UI 功能作为彼此独立的项目，而是把它们收敛成一个本地优先的 AI 编程协作工作空间。

产品由三个层次组成：

- **桌面客户端：** 提供稳定的 Electron 窗口、单实例、托盘、启动恢复和安装包。
- **协作内核：** 统一管理 Claude Code、Codex、内置智能体和 Web 控制台的身份、状态、上下文与消息。
- **开源交付：** 提供跨平台构建、数据库迁移、配置迁移、测试、文档和版本发布能力。

### 1.1 成功标准

完成第一轮产品化后，用户应当能够：

1. 通过一个桌面入口启动 Conflux，不需要手动启动 Vite、Fastify 或浏览器。
2. 在 5 秒内看到当前 Codex/Claude 会话，并能区分运行时、项目和会话标题。
3. 关闭并重新打开客户端后，不产生重复服务、孤立进程或重复会话节点。
4. 在不同 AI 会话之间搜索上下文、发送问题、查看回复和恢复工作现场。
5. 在 Windows 上安装和升级，并能从源码运行完整测试与构建流程。

### 1.2 非目标

本阶段不实现云端同步、远程多用户协作、账号体系、移动端、插件市场或托管数据库。所有核心数据仍然以本地 SQLite 为默认存储。

## 2. 产品定位与用户流程

Conflux 的主流程是「打开客户端 → 查看当前会话 → 选择协作动作 → 留下可搜索的结果」。图谱是关系视图，不再承担唯一的导航职责。

首屏需要提供：

- 当前活跃会话和最近活动。
- 按项目分组的会话列表。
- 待回复消息和最近共享上下文。
- 快速动作：查看上下文、发送问题、打开终端、复制会话信息。

图谱、会话列表、消息、上下文和运行时列表使用同一套查询与状态模型。用户从任何视图选中会话后，右侧详情区域展示该会话的标题、运行时、项目、在线状态、最近活动和可执行动作。

## 3. 目标架构

```text
Electron 主进程
  ├─ 单实例与窗口生命周期
  ├─ 本地服务生命周期
  ├─ 托盘与系统级动作
  └─ 安全边界与外部链接策略
       │
       ├─ 开发模式：Vite + Fastify
       └─ 生产模式：静态前端 + Fastify
              │
              ├─ HTTP API（桌面与 CLI 共用）
              ├─ MCP stdio 适配器（Codex / Claude）
              ├─ 会话身份与存活协调器
              ├─ 协作内核（上下文、消息、图谱）
              └─ SQLite 存储与迁移
```

### 3.1 边界原则

- `apps/desktop` 只负责桌面生命周期和平台能力，不直接读写业务数据库。
- `apps/web` 只通过 HTTP API 访问业务数据，不依赖 Electron 的 Node 能力。
- `apps/server/src/core` 是唯一的业务规则来源，HTTP、MCP 和 CLI 都调用它。
- MCP 继续使用 stdio，stdout 只输出 JSON-RPC，日志统一写入 stderr。
- Electron 桌面专属能力通过最小 preload API 暴露；业务数据不迁移到 IPC。
- 开发和生产模式共享核心 API，但使用不同的前端加载和服务启动策略。

保留 HTTP 边界可以继续支持 CLI、浏览器开发和外部脚本，同时避免把桌面客户端与 Electron API 强耦合。需要平台能力时，再通过 preload 增加最小的专用接口。

## 4. Electron 桌面运行时

### 4.1 开发模式

`npm run dev:desktop` 是唯一推荐入口。Electron 主进程启动 Fastify 和 Vite，等待健康检查通过后加载 Vite 页面。`npm run dev:all` 继续保留为纯浏览器开发入口，但不能与 Electron 模式同时运行。

开发模式必须具备：

- 服务启动前检查端口占用，并报告具体端口和进程来源。
- 对自己启动的进程建立进程树记录，退出时递归清理。
- 使用单实例锁，避免重复窗口和重复服务。
- 启动超时、子进程提前退出和页面加载失败都显示可操作的错误信息。
- 开发缓存写入 `.electron-dev`，该目录不进入 Git。

### 4.2 生产模式

生产模式不启动 Vite，不依赖用户安装全局 `npm` 或 `tsx`。构建阶段生成 `apps/web/dist` 和 server 的可运行产物，Electron 主进程启动内置的 server 进程并加载其静态页面。

生产模式必须具备：

- 从应用安装目录解析 server 和静态资源路径，不依赖当前工作目录。
- server 只绑定 `127.0.0.1`，启动后把实际访问地址传给窗口。
- 若默认端口已被占用，显示端口占用诊断，而不是静默连接到未知服务。
- 应用退出、崩溃和二次启动时清理或接管自己创建的服务。
- 使用 `app.requestSingleInstanceLock()` 保证一个用户数据目录只对应一个窗口实例。

### 4.3 Electron 安全基线

继续保持 `contextIsolation: true` 和 `nodeIntegration: false`，并补充以下策略：

- 为生产页面设置明确的 Content Security Policy。
- 默认阻止窗口内导航到非 Conflux 地址。
- 外部链接通过系统浏览器打开，不在业务窗口中加载。
- 生产环境关闭宽松的 CORS 配置，开发环境仅允许本地开发地址。
- preload 只暴露 `isElectron`、平台信息和必要的桌面动作，不暴露 `fs`、`child_process` 或数据库连接。

## 5. 会话身份与存活模型

当前问题的根源是「MCP 连接」「运行时进程」和「AI 对话会话」混用。下一阶段明确三种对象：

### 5.1 逻辑会话（Session）

逻辑会话代表用户可以阅读、搜索和通信的 AI 对话。它使用稳定的 `session_id`，优先采用 Claude/Codex 能提供的会话 ID；无法获得时使用 MCP 连接生成的 UUID。

会话字段至少包括：

- `id`：稳定的逻辑会话 ID。
- `name`：标题，优先级为自定义标题、首条任务摘要、项目目录名。
- `description`：当前工作内容的短摘要。
- `project_dir`：工作目录。
- `runtime`：`claude`、`codex`、`internal` 或 `web`。
- `status`：`active`、`stale` 或 `ended`。
- `last_heartbeat_at`：最近一次确认在线时间。
- `identity_source`：`hook`、`mcp`、`http`、`cli` 或 `internal`。

`temp` 只表示身份仍可被更准确的运行时会话接管，不再决定是否显示。活动的 MCP 会话必须可见；进程退出并超过 TTL 后才隐藏或回收。

### 5.2 运行时实例（Runtime Process）

运行时实例代表一个实际的 Claude/Codex 进程，记录运行时、PID、启动时间、最近探测时间和所属逻辑会话。PID 只是存活探测线索，不能作为逻辑会话的主键。

探测策略：

- MCP 连接启动时立即注册并写入运行时信息。
- MCP 每 30 秒发送 heartbeat。
- HTTP server 每 30 秒探测 Claude 和 Codex 进程，并刷新或回收运行时绑定。
- 无法探测进程时使用 heartbeat TTL，避免一次 PowerShell 或系统调用失败误杀会话。
- `/resume` 发生时，优先根据运行时 PID、固定映射和 transcript lineage 重新绑定逻辑会话。

### 5.3 MCP 连接

每个 Codex/Claude MCP 子进程对应一个连接生命周期。连接启动后自动创建或接管一个逻辑会话；`register_session` 用于补充标题、描述和技能卡，而不是连接可见性的前置条件。

Codex 没有 Claude Hooks 时，MCP 连接仍然是有效会话，UI 显示运行时为 Codex，标题暂时使用项目目录名，直到客户端或用户提供更明确的名称。

## 6. 协作内核

### 6.1 会话列表与图谱

- 活跃会话按最近心跳排序，并支持运行时、项目、状态和关键词过滤。
- stale 会话进入折叠区域，默认不占据首屏。
- 图谱默认显示活跃会话、活跃内置智能体和有通信记录的节点。
- 临时节点只有在 active 时可见，失效后不再制造 UUID 噪音。
- 选中会话时，详情面板展示统一的身份和生命周期信息。

### 6.2 上下文与消息

核心动作保持现有 MCP、HTTP 和 CLI 语义一致：

- 发布上下文：标题、正文、标签、来源会话。
- 查询上下文：全文检索、会话过滤、标签过滤和结果排序。
- 发送问题：显示目标当前状态，目标离线时明确提示异步投递。
- 回复问题：保留原通信通道，不创建重复反向边。
- 会话恢复：打开正确的项目目录和运行时命令，并保留消息继承关系。

UI 增加消息状态、失败重试、复制内容和上下文来源跳转；删除或结束操作必须有确认和可追踪审计记录。

### 6.3 运行时智能体

运行时预设与一次性会话分开管理。预设只描述启动参数、模型和工作目录；每次启动创建一个运行时实例并绑定一个逻辑会话。启动器必须返回可追踪的实例 ID、PID 和失败原因。

## 7. 数据、配置与迁移

### 7.1 SQLite

继续使用 SQLite WAL，但补充：

- 明确的 schema migration 版本和失败回滚提示。
- 应用退出和定期空闲时执行 checkpoint，避免 WAL 无限增长。
- 导出功能生成包含会话、上下文、消息和智能体配置的版本化 JSON 文件。
- 导入功能先执行格式校验，再以事务写入，遇到冲突提供覆盖、跳过和生成副本三种策略。
- 数据库损坏或锁冲突时给出数据目录和恢复建议，不显示原始堆栈作为唯一错误。

默认仍使用 `~/.muiltchat`，同时引入配置迁移层：

- 新变量使用 `CONFLUX_HOME`，继续读取 `MUILTCHAT_HOME`。
- 新 CLI 命令使用 `conflux`，保留 `muiltchat` 兼容入口。
- MCP server key 默认使用 `conflux`，旧的 `muiltchat` key 继续可用。
- 第一次启动时不自动删除旧目录；完成迁移后保留可回滚的备份标记。

### 7.2 密钥与敏感配置

API key 不应通过普通会话列表、日志、审计详情或错误栈输出。设置页面只显示是否已配置，不回显完整值。短期继续兼容环境变量，长期将桌面端敏感配置迁移到操作系统凭据存储；数据库中只保留引用或加密后的值。

## 8. 前端工作空间

首屏布局采用「导航 + 当前工作区 + 详情」结构：

- 导航：会话、消息、上下文、智能体、运行时、设置。
- 当前工作区：列表、时间线或图谱，根据导航切换。
- 详情面板：当前选中会话或消息的完整信息和动作。

必须补齐以下体验：

- 当前会话置顶和清晰的运行时标识。
- 会话列表的搜索、状态筛选和项目分组。
- 消息待处理数量和错误重试状态。
- 上下文搜索结果的来源会话、更新时间和跳转。
- 无数据、加载中、断线、服务启动中和服务崩溃状态。
- 长文本截断、复制、展开和键盘操作。

图谱继续保留，但不把图谱节点名称作为唯一身份提示；所有节点必须能够打开详情并执行下一步动作。

## 9. 开源工程与发布

### 9.1 仓库质量

- 根目录 README 中文优先，英文文档保持同步。
- 增加贡献指南、变更日志、行为兼容说明和故障排查文档。
- 通过 GitHub Actions 执行 server 测试、desktop 测试、完整构建和最小启动检查。
- 使用 Conventional Commits，提交主题保持可生成变更日志。
- 对公开配置、日志和示例进行敏感信息扫描。

### 9.2 构建与发行

采用 Electron Builder 生成 Windows 安装包，随后增加 macOS 和 Linux 构建矩阵。每个平台至少包含：

- 开发构建检查。
- 生产资源加载检查。
- 安装后首次启动检查。
- 服务退出清理检查。
- 数据目录迁移检查。

自动更新、代码签名和发布渠道在第一版安装包稳定后接入，不阻塞本地开发和手动下载发行。

## 10. 分阶段计划

### 阶段一：运行时基础与会话可信度

目标是让「一个桌面入口 + 一个当前会话」稳定工作：

- 开发模式单实例和服务拥有关系。
- 生产模式加载静态前端并启动内置 server。
- 会话身份字段和 MCP/运行时绑定规则统一。
- 活跃 Codex/Claude 会话在列表、图谱和详情中一致显示。
- 补充数据库迁移、heartbeat 和异常恢复测试。

验收：新启动的 Codex 会话在 5 秒内可见；关闭 Electron 后不会留下它创建的服务进程；重复启动不会产生第二套端口监听。

### 阶段二：日常协作工作流

目标是让用户无需绕路即可完成跨会话协作：

- 当前会话工作区和最近活动首屏。
- 上下文、消息、时间线和详情面板闭环。
- 运行时智能体启动、停止、恢复和错误提示。
- 搜索、过滤、复制、重试和审计体验。

验收：用户可以从当前会话找到另一个会话，发布上下文、发送问题、查看回复，并从详情恢复目标运行时。

### 阶段三：开源可交付版本

目标是让陌生用户可以安装、运行、升级和贡献：

- Windows 安装包和生产启动路径。
- `muiltchat` 到 `Conflux` 的兼容迁移。
- CI、变更日志、贡献指南和跨平台构建矩阵。
- 导入导出、备份恢复和升级失败诊断。

验收：新机器可以按照 README 完成安装；旧数据升级后仍可读取；Pull Request 能自动完成测试和构建检查。

## 11. 测试策略

测试按边界分层：

- **Core 单元测试：** 会话身份、状态转换、心跳、进程绑定、消息、上下文和迁移。
- **接口测试：** HTTP、MCP 和 CLI 对同一业务动作返回一致结果；MCP stdout 不混入日志。
- **桌面运行时测试：** 单实例、服务启动/退出、端口冲突、生产资源路径和外部导航拦截。
- **端到端测试：** 启动 Electron，确认页面加载、当前会话可见、列表刷新和一次消息流程。
- **发布冒烟测试：** 安装包启动、数据库迁移、升级后启动和卸载后的数据保留。

每个涉及会话生命周期的缺陷必须先添加可复现测试，再修改实现。完成声明必须包含实际运行的测试命令和退出状态。

## 12. 风险与取舍

### 保留 HTTP 还是改成 IPC

本阶段保留 HTTP 作为业务边界，避免破坏浏览器、CLI 和 MCP。IPC 只用于窗口、托盘和系统级动作。这样会保留本地 API 的安全责任，但迁移成本和生态兼容性更可控。

### 固定端口还是动态端口

开发模式继续使用 9527 和 5173，便于调试。生产模式固定使用 9527，并在启动前确认端口属于当前 Conflux 实例；若被未知进程占用，直接显示端口诊断并退出，不连接未知服务，也不自动回退到其他端口。

### 全局数据还是项目数据

默认继续使用全局数据库，满足跨项目协作；项目级数据库作为显式选项保留。界面必须显示当前数据范围，导出和迁移也必须携带范围信息，避免用户误以为不同数据库共享数据。

## 13. 明确不改变的兼容行为

- 现有 MCP stdio 接口继续可用。
- 现有 HTTP 路径和 CLI 主要命令保持兼容。
- 现有 `.mcp.json` 可以继续使用旧 server key。
- `~/.muiltchat` 中已有会话、消息、上下文和智能体不因升级自动删除。
- Claude Hooks 和 Codex 的进程探测同时保留。
